# "What's new" button Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A "What's new" button on the Upgrade screen shows the release notes between the chosen stick's version and the release to be written.

**Architecture:** Every stick gets a `version` file beside its kernel; `thinfloe-upgrade drives` reports it. A new batch command `thinfloe-upgrade notes` fetches the tag-pinned `CHANGES.md` and prints the sections in range. The menu runs it as a job, parses the printed Markdown into headings and bullets, and shows them in a dialog.

**Tech Stack:** Python 3 (`overlay/usr/bin/thinfloe-upgrade`, unittest in `test/unit/`), Rust + egui/shadcn-egui (`src/thinfloe-menu`), shell (`scripts/make-bootable-image.sh`).

**Spec:** `docs/superpowers/specs/2026-11-16-whats-new-design.md`

## Global Constraints

- Notes URL: `https://raw.githubusercontent.com/oposs/thinfloe/v<to>/CHANGES.md`; no GitHub API; release assets stay exactly six.
- No button for a source entered by hand (`custom` release / `Advanced` source in use).
- Dev versions `X.Y.Z-dev+sha[.dirty]` compare as `X.Y.Z`; `## [Unreleased]` is never printed.
- Plain wrapped text, backticks removed; no Markdown renderer crate.
- UI colours from the theme, sizes from named constants in `brand.rs` (`ui_code_has_no_style_literals`); lyra, nothing rounded.
- Every child of `thinfloe-upgrade` runs with `**SPAWN`; `tf_log`-style rule: diagnostics to stderr only, the notes alone on stdout.
- Builds/tests: max 4 cores; `systemd-run --user --scope -q -p MemoryMax=4G --` around cargo and make test; `TMPDIR=/scratch/oetiker/claude-tmp/thinfloe-tests/whatsnew`.
- `CHANGES.md` `[Unreleased]` `### New` gets one entry (Task 5).

## Review Focus

1. A `version` file on a stick holding junk (binary, 10 MB, a newline-only file): `drives` must report `version: null`, never fail the listing. → Task 1 test `test_drives_version_junk_is_null`.
2. A `CHANGES.md` at the tag that is not ours (an HTML 404 page served 200, or a huge file): `notes` exits non-zero with a reason, prints nothing on stdout. → Task 2 tests `test_notes_no_sections_fails`, `test_notes_too_big_fails`.
3. A stick already at or above the target (downgrade, same version): the panel says "No changes between <from> and <to>", not an empty box. → Task 2 `test_notes_empty_range_exits_3` and Task 4 `notes_empty_range_text`.
4. The person changes the chosen stick or mode while notes load: a late result for the old (from, to) must not be shown for the new choice. → Task 3 test `late_notes_for_another_range_are_dropped`.
5. A bullet that continues on an indented next line in `CHANGES.md`: it stays one bullet. → Task 3 test `parse_joins_continuation_lines`.

**Interfaces:**
- Produces CLI: `thinfloe-upgrade notes --to X.Y.Z [--from A.B.C]`. stdout: the selected sections verbatim (`## X.Y.Z - date` line and its body up to the next `## `), newest first, as in the file. - Version compare: parse `X.Y.Z` from the start of each value (strip `-…` and `+…`); `--to` and `--from` must match `VERSION_RE`, else exit 2 via the parser's error.

Use `capture_as` (stderr kept) with `NOTES_BYTES: usize = 512 * 1024`, `NOTES_TIMEOUT = 40 s`; log source as the other upgrade calls.
- Produces in `upgrade.rs`: `UpgradeEvent::WhatsNew`, `UpgradeEvent::CloseNotes`; `Request::Notes { from: Option<String>, to: String }`; `pub enum Notes { Closed, Loading { from: Option<String>, to: String }, Shown { from: Option<String>, to: String, lines: Vec<Line>, unknown_from: bool }, Empty { from: String, to: String }, Failed(String) }` as field `pub notes: Notes`; `pub fn notes_range(&self) -> Option<(Option<String>, String, bool)>` (from, to, unknown_from): `None` without a target version or with the custom source in use; Fresh mode or no chosen drive → `(None, to, false)`; Upgrade mode → `(drive.version, to, drive.version.is_none())`; `pub fn on_notes(&mut self, from: Option<String>, to: String, result: Result<Option<String>, String>)` ignores a result whose (from, to) differs from `Loading`'s.
